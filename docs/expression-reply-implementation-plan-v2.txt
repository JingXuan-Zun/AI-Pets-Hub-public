0. 实施目标与范围

将现有“表情包设置 + 单图库管理”接通为可实际工作的桌宠表情回复能力。实现范围包括：

1. 一个主根目录、多个拓展根目录和多个用户自定义根目录；
2. 根目录下的一级分类、图片自动分类建议和必须经过用户审核的批量审核流；
3. 两种成套表情包导入方式：应用托管库导入、用户外部目录只读导入；
4. 用户可调整每个根目录的自动回复优先级；
5. 桌宠可把同一条回复分成多个语义片段，分别选择图片表情、颜文字或 Emoji；
6. 图片渠道仅使用已审核、可读取、已启用根目录中的图片；
7. 提供经过产品内置分类、不可删除的 Emoji 与颜文字只读表情库；
8. 聊天记录以稳定引用保存桌宠所用图片；用户上传图片采用去重快照治理；
9. 资源失效时静默降级为文字，并在设置工作区或日志给出诊断。

本文件不是界面功能介绍，而是实现顺序、状态约束、数据结构、算法、接口和验收标准。


1. 已确认的产品决策

1.1 根目录模型

根目录是用户理解与管理表情包的最小来源。一级分类是桌宠选择图片时的主要语义容器。

表情包系统
├─ 主根目录：我的表情包
│  ├─ 开心
│  ├─ 疑惑
│  └─ 用户自建的其他一级分类
├─ 拓展坞
│  ├─ 拓展根目录：角色专属表情包
│  ├─ 拓展根目录：节日表情包
│  └─ 用户上传的其他成套表情包
└─ 自定义根目录
   └─ 用户自行创建、命名与管理的根目录

约束：

- 用户只能拥有一个逻辑上的“主根目录”。它默认名为“我的表情包”，但允许改名。
- 拓展根目录由用户导入成套表情包时自动创建，逻辑上与主根目录平行。
- 用户可手动创建任意数量的自定义根目录。
- 每个根目录都可以独立启用或停用“参与桌宠自动回复”。
- 用户可通过拖动排序或数字调整，设置每个根目录的回复优先级；不是固定强制主根目录永远第一。
- 初始默认值：主根目录优先级最高；后导入的拓展根目录依次排在其后；用户调整后完全以用户顺序为准。

1.2 图片表情权重为 0 的真实前置条件

图片表情初始权重为 0 的原因，不是“用户必须先明确拖动滑块才能参与选择”，也不是“系统没有根目录或一级分类”。系统默认已经有主根目录及“开心”“伤心”两个一级分类。

图片表情为 0 的直接原因是：默认一级分类文件夹内尚未导入任何图片，因此不存在“已审核且可读取”的图片候选。

实现规则：

- imageLibraryEnabled = true 只表示用户允许使用图片表情库。
- 当不存在“已启用根目录中的至少一张已审核且可读取图片”时，图片渠道的 effectiveWeight 必须是 0。
- 默认根目录和“开心 / 伤心”分类存在但为空时，设置页应显示原因，例如“默认分类中暂无已审核图片，图片表情暂不可参与回复”。
- 此时图片权重滑块禁用或显示为 0；不能让 UI 看起来可用而实际永远选不到图。
- 首个可用根目录、分类和已审核图片建立后，图片滑块恢复可编辑，但当前权重仍保持 0，避免系统未经用户意愿突然开始发图。
- 用户之后设置非零图片权重，图片渠道才会进入实际选择；这一步是“用户配置比例”，不是图片权重初始为 0 的原因。

为同时保存用户设置意图和运行时可用性，配置中应区分：

configuredImageStickerWeight：用户设置的图片权重。
effectiveImageStickerWeight：本轮候选集计算后的有效图片权重。

有效权重计算：

if 图片库关闭 or 没有可用已审核图片:
  effectiveImageStickerWeight = 0
else:
  effectiveImageStickerWeight = configuredImageStickerWeight

颜文字和 Emoji 与图片一起按有效权重重新归一化。配置页展示 configured 值，运行状态展示 effective 值和不可用原因。


2. 根目录与一级分类生命周期

2.1 主根目录初始化

系统首次初始化时即创建受控主根目录“我的表情包”，并创建两个默认一级分类：“开心”和“伤心”。这两个分类可为空；空分类不代表根目录不可用，只代表当前没有图片候选。

实现流程：

1. 应用初始化时：
   - 创建或恢复 sourceType = main、name = 我的表情包 的受控主根目录；
   - 创建或恢复“开心”“伤心”两个一级分类的记录和受控文件夹；
   - 默认分类为空时，图片渠道有效权重为 0，但 Emoji 与颜文字渠道仍可工作。
2. 用户点击“新建分类”时：
   - 在当前选定根目录下自动创建用户填写名称对应的一级分类文件夹与分类记录；
   - 不要求用户在资源管理器中手动建目录；
   - 新分类导入图片后，图片进入 needs-review；审核通过至少一张图片后，该分类才可用于图片回复。
3. 用户导入第一张图片并通过审核后：
   - 根目录仍保持原有状态；
   - 图片候选集开始非空；
   - configuredImageStickerWeight 若为非零，图片渠道立即拥有相同的 effectiveWeight；若配置仍为 0，保持 0。

因此，用户新建分类时会自动生成其对应的一级分类文件夹；主根目录与“开心 / 伤心”默认分类不需要等待用户首次建分类才生成。

2.2 自定义根目录创建

用户点击“新建根目录”后选择：

- 名称；
- 类型：受控目录（由应用管理）或外部只读目录（选择现有文件夹）；
- 是否立即参与自动回复；
- 初始回复优先级。

受控目录：应用创建根文件夹，并允许导入、分类、移动、重命名和删除。

外部只读目录：用户选择已有根文件夹，应用只扫描与建立索引；绝不移动、重命名、复制、删除或写入该外部目录内的图片和分类文件夹。

2.3 删除最后一个一级分类

根目录不应在用户删除最后一个分类时被静默删除。必须弹出明确确认，并根据根目录类型执行不同事务。

前置检查：

- 若最后一个分类仍有图片，先要求用户选择：批量移动到其他根目录/分类、排除保留、或在受控目录中删除图片。
- 未处理图片、待审核图片或导入任务运行中时，不允许完成根目录删除。
- 删除根目录前必须显示将影响的分类数量、图片数量和是否会影响磁盘文件。

确认后的规则：

1. 主根目录：
   - 逻辑主根目录回到 uninitialized，而不是消失；这样用户后续可再次“新建分类”并自动重建主根目录。
   - 受控物理目录仅在确认“同时删除空目录”后删除；若空目录保留也不影响功能。
   - 主根目录不再含一级分类时，图片渠道 effectiveWeight 立刻变为 0。

2. 受控拓展根目录或受控自定义根目录：
   - 确认后移除根目录记录；
   - 若根目录为空，应用可删除物理空目录；
   - 若用户选择删除其中图片，使用可恢复删除（系统回收站或应用隔离回收区），不得直接不可逆删除。

3. 外部只读根目录：
   - 只移除应用中的“连接 / 索引记录”；
   - 外部根目录、分类与图片绝不删除或修改；
   - UI 文案应为“停止读取此目录”，不能写成“删除文件夹”。


3. 两种成套表情包导入方式

3.1 导入方式 A：导入应用托管库

适用场景：用户获得一整套图片表情包，希望应用代为保存、整理和管理。

用户流程：

1. 点击“拓展坞 -> 导入成套表情包 -> 导入应用托管库”。
2. 选择一个本机文件夹。
3. 应用创建新的受控拓展根目录，与主根目录平行。
4. 应用将图片复制到自己的受控根目录；原始文件夹不被删除。
5. 应用读取原始一级文件夹、文件名和图片内容，生成一级分类建议。
6. 每张图片均标记为 needs-review，进入批量审核工作区。
7. 用户批量审核通过后，该拓展根目录可启用参与桌宠自动回复。

受控库能力：

- 可批量移动图片；
- 可新建、改名和删除一级分类；
- 可在分类间移动文件；
- 可移除图片；
- 可按需由应用维护缩略图、哈希和索引；
- 所有破坏性操作需要明确确认，并优先可恢复。

3.2 导入方式 B：连接外部目录库（用户自行分类）

适用场景：用户已经在资源管理器中按自己的方式整理好一套表情包，不希望应用碰原始文件。

用户流程：

1. 用户在外部目录完成一级分类；一级子文件夹即其分类。
2. 点击“拓展坞 -> 连接外部目录库”。
3. 选择外部表情包根目录。
4. 应用创建一个 external 类型根目录并扫描该目录。
5. 应用把外部一级子文件夹建立为只读分类索引，图片建立为只读 asset 索引。
6. 应用显示一次“导入预览 / 批量确认”：用户确认这些分类可用于自动回复，或把不适用图片标记为排除（排除记录只写入应用索引）。
7. 用户启用该根目录后，已确认、可读取图片才参与桌宠回复。

外部目录只读约束：

- 应用不得复制、移动、删除、重命名外部图片；
- 应用不得创建、删除或重命名外部分类文件夹；
- 用户若要重新整理图片，必须在资源管理器中完成；应用只提供“打开文件夹”和“重新扫描”；
- 应用内的审核状态、排除状态、哈希和分类描述写入用户数据索引，不写入外部文件夹；
- 外部图片删除、移动或改名后，下一次扫描应标为 unavailable，自动回复自动降级。

3.3 导入方式选择 UI

同一个入口明确显示两个卡片，避免用户误以为两者相同：

“导入应用托管库”
  复制一份到应用管理的表情包库；可在应用内分类、移动、删除。

“连接外部目录库”
  保持当前文件夹不变；应用仅读取与建立索引，所有整理在资源管理器完成。


4. 自动分类与用户批量审核

4.1 分类输入与输出

对于应用托管导入，自动分类 Module 输入：

- 原始一级目录名；
- 原始相对路径；
- 文件名；
- 图片视觉内容；
- 已有分类名称与描述；
- 用户过去对同一导入包作出的修正。

输出：

- 建议一级分类；
- 分类置信度；
- 候选分类列表；
- 简短理由；
- 是否应进入未分类。

分类结果不直接改变“可自动回复”资格。无论置信度如何，新图都先为 needs-review。

4.2 审核工作流

导入完成后自动打开现有批量审核与批量移动区域：

1. 按建议分类展示缩略图网格；
2. 用户可勾选单图、多图或某分类全部；
3. 可执行：批量通过、批量移动、批量排除、创建分类、修改分类；
4. 批量通过将图片状态变为 accepted；
5. 批量移动后，图片回到 needs-review，要求在新分类内再次通过；
6. 分类名称或描述修改后，该分类下 accepted 图片回到 needs-review；
7. 批量排除后，图片保持可预览但不能自动使用。

4.3 外部目录审核差异

外部目录图片无法在应用中移动。审核区只允许：

- 批量通过；
- 批量排除；
- 为只读分类保存描述；
- 打开外部分类文件夹；
- 重新扫描。

“移动到分类”在外部目录模式中应替换为“请在资源管理器中移动后重新扫描”。


5. 根目录优先级与候选选择

5.1 用户配置

每个根目录保存：

{
  id: string,
  name: string,
  sourceType: 'main' | 'expansion' | 'custom',
  storageMode: 'managed' | 'external-readonly',
  enabledForReply: boolean,
  replyPriority: number,
  status: 'uninitialized' | 'review-required' | 'ready' | 'unavailable'
}

设置页提供根目录列表。用户可：

- 开关“参与自动回复”；
- 拖动根目录顺序；
- 修改名称；
- 查看“已通过 / 待审核 / 失效”图片数量；
- 打开受控或外部文件夹；
- 删除或停止连接根目录。

replyPriority 由列表排序生成。用户排在最上面的根目录优先级最高。主根目录仅提供默认最高优先级，不覆盖用户后续排序。

5.2 候选过滤

图片候选必须同时满足：

- 根目录 enabledForReply = true；
- 根目录 status = ready；
- 分类存在且未要求重新审核；
- 图片 classificationStatus = accepted；
- 图片 available = true 且发送前仍可读取；
- 图片没有落入当前桌宠、当前会话的近期去重窗口；
- 分类的名称、描述或图片级标签与当前语义片段相匹配。

5.3 图片选择

Agent 不可选择路径、文件名或 assetId。Agent 只产生有限数量的语义片段，例如：

[
  { range: '主人这么关心我，我好开心呀！', intent: '开心' },
  { range: '不过主人什么时候来吃饭呀？', intent: '疑惑 / 关心' }
]

本地应用对每一个语义片段：

1. 取得按 replyPriority 排序的根目录；
2. 在优先级最高且语义匹配的根目录中寻找候选分类；
3. 在候选分类中筛选 accepted、available、未近期重复图片；
4. 当图片渠道被权重算法选中时，选择具体 assetId；
5. 首选根目录无候选时，继续尝试下一个已启用根目录；
6. 所有图片候选失败时，降级到颜文字、Emoji 或纯文字。

同一条回复可以对“开心”和“疑惑”分别从不同根目录中选图。根目录优先级只解决“多个图库都能表达同一语义时优先使用哪个”，不会限制多语境回复。


6. 回复方式占比与多语境决策

6.1 可用性与有效权重

每条回复先由 Agent 识别 0 至 2 个语义片段；特别复杂回复最多 3 个。

对每个语义片段独立计算：

- 图片有效权重：由根目录、分类、审核状态、资源可用性和 configuredImageStickerWeight 决定；
- 颜文字有效权重：由 kaomojiWeight 与可用颜文字池决定；
- Emoji 有效权重：由 systemEmojiWeight 与可用 Emoji 池决定。

若一个渠道无候选，其有效权重为 0，其余渠道重新归一化。全部渠道均无候选或总开关关闭时，不插入表情，保留纯文字。

6.2 调度算法

不能使用“每次纯随机抽取”，因为用户在少量对话中会明显感觉比例失真。

使用加权公平调度 Module：

- 状态按 petId + conversationId 维护；
- 每成功插入一个表情位置，更新各渠道的累计配额；
- 下一次优先选择欠配额最多的有效渠道；
- 0 / 30 / 20 时，图片永远不选；在足够多的有效位置上，颜文字与 Emoji 稳定趋近于 60% / 40%；
- 某渠道暂时无候选时不累计“必须补发”的债务，恢复后按当前有效候选重新开始，避免突然连续发图。

6.3 去重与降级

- 图片去重键：assetId。
- 颜文字和 Emoji 去重键：实际 token。
- 历史作用域：petId + conversationId。
- 首先排除最近 N 条；若候选不足且所有候选均被排除，可选择一次最久未用项，避免完全失去表情能力。
- 发送前再次读取验证图片；失败则不写图片片段，回退到下一渠道或纯文字。


6.4 内置 Emoji 与颜文字只读表情库

当前系统尚未具备 Emoji 与颜文字候选池。应新增一个随应用发布、由产品维护的“系统文本表情库”，让现有 Emoji 和颜文字权重具有真实候选，而不要求用户先导入这些文本表情。

系统文本表情库不是用户图库，也不是外部目录。它是一个只读 Module：

- sourceType = system；
- storageMode = bundled-readonly；
- 保存位置与用户上传图片、应用用户数据目录完全分离；
- 开发环境保存于应用项目资源目录：resources/system-expressions/catalog.json；
- Windows 打包后保存于应用包内：win-unpacked/resources/app.asar/resources/system-expressions/catalog.json；运行时通过 app.getAppPath() 读取，不从用户的“表情包”目录或 userData 读取；
- Emoji 与颜文字本身是 token，不需要复制成图片文件；分类、token、稳定 id 和说明保存在 catalog.json；若后续增加自定义图标或精灵资源，也只能放在同一应用包资源目录；
- 由随应用发布的只读 manifest 定义；
- 根目录、分类、Emoji、颜文字均不可由用户删除、移动、改名或修改内容；
- 用户仍可通过“Emoji 权重”“颜文字权重”或总开关控制它们是否参与回复。

建议将 Emoji 与颜文字放进同一个逻辑根目录“系统文本表情”，按语义分类，而不是按字符格式分类：

系统文本表情（只读）
├─ 开心：😊、😄、(≧▽≦)、(｡•̀ᴗ-)✧
├─ 伤心：😔、🥺、(｡•́︿•̀｡)、(´；ω；`)
├─ 疑惑：🤔、❓、(・_・?)、(⊙_⊙)?
├─ 关心：🙂、🫶、(｡･ω･｡)ﾉ♡、( ´ ▽ ` )
├─ 庆祝：🥳、🎉、ヽ(✿ﾟ▽ﾟ)ノ、✧٩(ˊωˋ*)و✧

第一版每个分类保留少量、语义清晰且通用的 token；不要一次塞入大量网络流行语、攻击性表达或含义不稳定的字符。后续只能通过应用版本升级扩充 manifest，不从用户图库自动吸收 token。

建议 manifest 结构：

{
  version: 1,
  root: { id: 'system-text-expressions', name: '系统文本表情', immutable: true },
  categories: [
    { id: 'system-happy', name: '开心', description: '开心、被关心、轻度庆祝。', immutable: true }
  ],
  assets: [
    {
      id: 'system-emoji-happy-smile',
      categoryId: 'system-happy',
      kind: 'emoji',
      token: '😊',
      immutable: true
    },
    {
      id: 'system-kaomoji-happy-grin',
      categoryId: 'system-happy',
      kind: 'kaomoji',
      token: '(≧▽≦)',
      immutable: true
    }
  ]
}

不可删除必须同时由三个层面保证：

1. 设置 UI：系统文本表情只读展示；不出现删除、移动、重命名、批量审核或编辑按钮。
2. Renderer Adapter：不向系统根目录发送可变更请求。
3. Electron 主进程 Implementation：所有针对 system 根目录、分类或 token 的删除、移动、改名、状态修改 IPC 一律返回失败；不能只依赖前端隐藏按钮。

系统 token 不需要用户批量审核，因为它们是产品随版本签入、人工维护的可信内容；但用户可以把 Emoji 或颜文字权重设为 0，从而让该渠道不参与自动回复。

应用包路径与用户路径必须严格分开：

应用包内（只读、随应用版本更新）：

win-unpacked/resources/app.asar/resources/system-expressions/catalog.json

用户受控图库（可导入、可移动、可删除）：

应用的受控“表情包”根目录及其主根目录、拓展根目录和自定义根目录。

外部目录图库（只读连接、文件仍归用户管理）：

用户自己选定的外部表情包文件夹。

用户设置和审核索引（可写，但不存储系统 token 内容）：

应用 userData 下的配置、根目录排序、外部库连接记录、审核状态与近期去重历史。

不得把系统 catalog.json 首次启动时复制进 userData 后再读取；否则用户删除或修改用户数据就会改变内置 Emoji / 颜文字的内容与分类，也会破坏“随应用发布、不可删除”的约束。

系统表情与用户图片统一接入回复 Runtime：Agent 先输出“开心 / 疑惑 / 关心”等意图，本地再依据本轮有效权重选择 image、emoji 或 kaomoji。若图片库为空而 Emoji / 颜文字内置库可用，0 / 30 / 20 会自然变为 0% 图片、60% 颜文字、40% Emoji。


7. 聊天消息、资源引用与用户图片快照

7.1 桌宠回复内容

ChatMessage 需要新增有序内容片段，而不是仅在消息末尾挂一张图片：

content: [
  { kind: 'text', text: '主人这么关心我，我好开心呀！' },
  {
    kind: 'expression',
    expressionKind: 'image',
    libraryRootId: 'root-main',
    categoryId: 'cat-happy',
    assetId: 'asset-001',
    selectionReason: '开心'
  },
  { kind: 'text', text: '不过主人什么时候来吃饭呀？我可以先帮你热好。' }
]

图片只保存 assetId、根目录与分类快照，不保存本机绝对路径。renderer 通过受控 IPC 获取预览；Agent 永远不接触路径。

7.2 用户上传图片

用户上传的图片与桌宠图库图片不是同一概念：

- 用户图片：用于模型阅读，初始可由 dataUrl 接收；后续写入图片仓库并获得 imageRef / contentHash。
- 图库图片：用于桌宠回复，通过 assetId 引用。
- 用户可以明确点击“加入表情包库”；届时复制到受控根目录或由外部目录重新扫描，并创建 assetId。

去重策略：

- 完全一致图片：SHA-256 相同，复用一个图片仓库对象；
- 相似图片：感知哈希提示“疑似重复”，但不自动合并；
- 长期记忆默认保留文字化语义，不无限保存每一张原图；
- 桌宠自动表情仅保留选择记录，不重复保存图片本体。

7.3 失效资源与提示位置

如果 assetId 指向的图片已经被删除或无法读取：

- 本轮聊天静默返回纯文字或其他可用渠道；
- 不在聊天气泡中显示“资源已删除”；
- 在表情包工作区的状态栏、诊断页或运行日志记录：时间、根目录、assetId、失败原因、建议操作“重新扫描”；
- 历史消息隐藏失效图片，仅保留原文字。


8. 实现 Module、Seam 与文件任务

为避免把根目录、审核、比例、去重、选图逻辑散落在聊天代码中，建立一个深 Module：ExpressionReplyRuntime。

对外 Interface：

resolveExpressionReply({
  replyText,
  petId,
  conversationId,
  replySettings,
  catalog,
  recentHistory
}) => ExpressionContentSegment[]

该 Interface 的不变量：

- 返回 0 至 3 个表达片段；
- 不返回路径；图片只能以合法 assetId 返回；
- 只返回 accepted 且 available 的图片；
- 失败永远返回较少片段或空数组，不阻断文字回复；
- 根目录排序由 catalog 给出并已应用用户 priority。

Implementation 内部负责意图解析、候选过滤、比例调度、去重、降级和诊断。这样 Module 具有较高 Depth，聊天调用方只需使用结果；这为后续新增 GIF、音效或更多表达渠道提供 Leverage，也让问题集中在同一处获得 Locality。

主要 Seam：模型文本已完成、最终 ChatMessage 写入前。流式阶段仍可显示文字；结束后通过消息更新写入有序内容片段。

9. 分阶段实施顺序

阶段 A：默认主根目录、根目录数据迁移与多根目录索引

- 将当前单活动图库迁移为根目录列表；保留现有图库数据为主根目录。
- 新增 sourceType、storageMode、enabledForReply、replyPriority、status。
- 迁移必须幂等；旧版本只有一个图库时不丢失分类和 assetId。
- 确保主根目录“我的表情包”及默认“开心 / 伤心”一级分类在初始化后存在。
- 默认分类为空时保留图片渠道不可用状态，直到有图片通过审核。

验收：旧用户升级后原图库仍可见；可新增受控和外部根目录；用户可排序。

阶段 B：受控拓展导入、外部只读连接与删除事务

- 实现两种导入入口和明确文案。
- 受控导入复制资源；外部连接只扫描。
- 实现最后一个分类和根目录删除前置检查、确认和不同存储模式的删除规则。

验收：外部库的任何文件操作均不会由应用触发；删除外部根目录只停止读取；受控根目录删除可恢复。

阶段 C：自动分类接入审核与批量移动

- 自动分类结果写入建议分类，但所有新图片均为 needs-review。
- 接入现有批量通过、批量移动、排除和分类编辑流程。
- 分类更名或描述改变使相关已通过图片重新审核。

验收：用户可批量确认整批图片；未通过审核图片无法被回复候选查询选中。

阶段 D：图库候选查询、系统文本表情库与回复比例 Runtime

- 构造按用户 priority 排序的图片候选 catalog。
- 加入随应用发布、不可删除的 Emoji / 颜文字系统文本表情 manifest。
- 在 UI、renderer 和 Electron 主进程三层锁定系统文本表情库的不可变规则。
- 实现 effectiveWeight、加权公平调度、去重和发送前资源校验。
- 为不可用图库在设置页显示原因。

验收：默认“开心 / 伤心”分类为空时图片有效权重为 0；0 / 30 / 20 时绝不发图、且在文本表情库可用时稳定产生颜文字与 Emoji；多根目录同语义时遵守用户排序。

阶段 E：多语境回复、消息片段与渲染

- Agent 只输出有限语义片段；应用本地选 assetId。
- 引入 ChatMessage 有序内容片段。
- 在聊天回复完成时接入 ExpressionReplyRuntime。
- 按句子位置渲染图片、颜文字与 Emoji。

验收：一条“开心 + 疑惑”的桌宠回复可在不同句后显示不同表达；聊天资源失效时只显示文字。

阶段 F：用户图片去重、长期记忆和诊断

- 建立 contentHash / imageRef 图片仓库。
- 加入“把聊天图片加入表情包库”。
- 在日志与工作区展示静默降级诊断。

验收：重复上传同图不反复保存；用户能主动将聊天图片纳入图库；聊天框不显示内部资源错误。


10. 测试计划

10.1 单元测试

- 旧单根目录迁移为主根目录；迁移重复执行结果不变。
- 初始化后存在主根目录及“开心 / 伤心”默认一级分类；空分类时图片有效权重为 0。
- 删除最后分类：主根目录回到 uninitialized；外部根目录仅断开；有图片时阻止删除。
- 受控和外部根目录权限差异。
- 自动分类结果全部是 needs-review。
- accepted / excluded / unavailable 状态过滤。
- 系统文本表情根目录、分类和 token 的删除、移动、改名、状态修改请求均被主进程拒绝。
- 开发环境与打包后的 catalog.json 均从应用包路径读取；用户表情包目录和 userData 中不存在系统 token 的可写副本。
- 0 / 30 / 20 在默认图片分类为空时，颜文字和 Emoji 仍能按 60% / 40% 参与回复。
- configured 与 effective 图片权重的区别。
- 图片 0、颜文字 30、Emoji 20 的有效比例；图片候选存在时仍不得选图。
- 根目录 priority、近期去重、候选不足与发送前失效降级。

10.2 集成测试

- 导入成套表情包到受控库 -> 自动新根目录 -> 审核 -> 启用 -> 回复选图。
- 连接外部目录 -> 预览确认 -> 启用 -> 外部文件变动后扫描并降级。
- 用户排序两个根目录后，同一语义优先从排序更高根目录选图。
- 一条回复包含两个语义片段，按顺序写入和渲染。
- 图片选中后在发送前删除，聊天仅显示文字，日志有诊断。

10.3 人工验收

- 新用户可看到默认主根目录及“开心 / 伤心”分类；分类文件夹为空时，图片滑块显示不可用原因且有效权重为 0。
- 用户新建分类时，应用自动创建对应的一级分类文件夹。
- 用户能以两种方式导入成套表情包，并理解二者是否会改动源文件。
- 用户能批量通过、移动、排除自动分类图片。
- 用户能调整每个根目录的优先级。
- 用户关闭某拓展根目录后，该图库不再被桌宠使用。
- 资源问题只在工作区/日志提示，聊天框保持自然文字对话。


11. 交付与打包

本功能会修改 Electron 主进程、preload、资源索引、聊天消息结构、renderer 和设置页，属于打包结构与运行时链路的重大变更。

正式验收必须执行完整打包：

npm.cmd run dist:win:fresh

不得用普通增量包作为正式交付结论。完整包完成后，使用：

release/build-时间戳/win-unpacked/AI Desktop Pet.exe

完成手工验收；正式 portable 成品为：

release/build-时间戳/AI-Desktop-Pet-0.0.1.exe

打包验收还必须确认 system-expressions/catalog.json 已被包含在 app.asar 的应用资源路径中；不得被错误复制到用户“表情包”目录或 userData。若使用 electron-builder 的 files 配置，应将 resources/system-expressions/catalog.json 明确纳入应用包。


12. 完成定义

以下条件全部满足，才可宣布表情包回复功能完整开通：

1. 一个主根目录、多个拓展根目录和自定义根目录可被创建、连接、管理和排序。
2. 主根目录默认包含“开心 / 伤心”一级分类；新建分类会自动创建对应物理一级分类文件夹。
3. 删除最后一级分类不会静默删除根目录；受控与外部目录遵守不同安全规则。
4. 用户可设置所有根目录的自动回复优先级。
5. 成套表情包支持受控导入和外部只读连接两种模式。
6. 自动分类结果必须进入批量审核与批量移动流程；未审核图片不能自动回复。
7. 图片权重为 0 的不可用原因正确反映“默认分类或已启用根目录中没有已审核、可读取图片”。
8. 用户建立可用根目录与分类后，图片渠道可用，但不会未经用户配置而自动产生非零比例。
9. 桌宠可从同一回复中识别多个语义片段，并分别选取表达。
10. 选图严格遵守根目录 priority、审核状态、资源状态、比例和近期去重。
11. 聊天框按语义片段顺序显示表达；资源失效时静默保留文字。
12. 用户上传图片具有去重与语义化长期记忆治理，不会长期产生无序重复快照。
13. 内置 Emoji 与颜文字按固定语义分类、可参与回复、且不能被用户删除或修改。
14. 内置 Emoji 与颜文字只从应用包内 catalog.json 读取，不存在用户数据中的可写副本。
15. 单元测试、集成测试、人工验收和 dist:win:fresh 完整打包全部通过。
